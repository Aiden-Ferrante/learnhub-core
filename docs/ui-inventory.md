# UI overhaul inventory (v0.25.0 map phase, 2026-11-03)


## ?

LearnHub's frontend has 17 page/layout/loading files. There is one root layout and no nested layouts. Course work hangs off /courses/[courseId], whose home has 7 child routes (chapter, read, concepts, skeleton, packs, packs/[packKey], edit) plus practice. Top-level pages are /study, /process, /upload, /reader, /styleguide, /login, and / (which only redirects legacy hash links). All navigation goes through callback props: page.tsx files call router.push and pass onBack/onX handlers into surfaces. Only the header (AppNav, Breadcrumbs, HeaderBrand), TodayStrip and the user menu use real <Link>/<a> tags. The old practice session and old exam mode share one route, /courses/[id]/practice, reached from one button on the course home. ExamMode and MatchGame live only inside PracticeSession, so the frontend part of the deletion is clean. On the backend it is not clean: exam packs borrow the author/judge models from the practice extractor, and the pack grader tags its events with the same 'practice' kind. Course-home Fluency is computed from ext_practice review rows. The library due count (study-debt) counts every concept_reviews row, including prac- and pack- cards the Review drawer never serves. That last point is the most important finding. The 'Review: N due' tile and the header Study badge show a course-wide number. The tile opens a review drawer limited to one chapter (an `all: true` flag is silently dropped), and that drawer leaves out practice, pack and skeleton cards. So the count can never reach zero from the Review button, and after the practice session is deleted its prac- cards stay due forever. /reader and /styleguide are effectively hidden. /reader can only be opened from a pop-out in BookReader, which shows only when a book has no original PDF, so the Python-textbook PDFs never show it. /styleguide is linked from a small 'kit' link in the user menu, even though its own comment says it is unlinked. Navigation is inconsistent in several ways. There are two back affordances on every course page (header breadcrumbs plus each surface's own back button), and the back labels differ ('Back to course', 'Course', 'Back', the course title, 'All packs'). Breadcrumbs know only 3 of the 8 course sub-routes. One section is named 'Learn', 'Courses' and 'Library' in different places. Upload, Process, the planner and guided reading each have 2 to 4 duplicate entry points. Proposed structure: /library → /c/[id] (Today) → /c/[id]/{review, read/[[...scope]], concepts, skeleton, packs, packs/[key]}, plus /admin/{upload, process, courses/[id]/edit}. /reader becomes a ?popout=1 mode of read. /study is folded into the library page. /styleguide moves to /admin/kit.

## ?

LearnHub has three styling layers stacked on one dark zinc palette. (1) globals.css holds the shadcn hsl-triplet tokens plus learnhub-only scales: status, kind, paper, highlight and hljs. (2) fleet-study.css is the exam-pack theme. diff against the study:begin..study:end range of fleet-ui/fleet.css (lines 601-656) shows it is currently byte-identical. It reads --fleet-* variables that globals.css:16-30 aliases onto the app palette. (3) tailwind.config.ts maps the tokens to utilities, and it also maps Tailwind's own size names onto the fleet's six type steps. The two palettes match in value: converting fleet --fleet-accent oklch(0.65 0.19 250) gives exactly hsl 205 100% 50%, which is --primary/--brand, and ok/warn/danger convert exactly to --status-mastered/due/error. So there is one blue, not two. The real divergences are: ink on accent (shadcn --primary-foreground is zinc-950 at globals.css:118, while the study theme's --fleet-on-accent is zinc-50 at :24); fill colours used as text everywhere (text-brand, about 207 hits, and text-status-*, about 81), even though fleet KIT.md says fills are not safe as text and the -text tokens should be used for words; raw Tailwind palette colours in the recall grade scale; per-title decorative hues; and dead legacy CSS. The app is dark-only in fact: there are no dark: utilities and html has class="dark". The one light area is the paper reading surface, which is scoped and intentional. The kit is underused. There are 106 hand-written <button> elements against 31 files that import Button. Card markup is hand-rolled 36 times next to SectionCard (4 consumers). ListRow is used only by the styleguide. Exam packs (pack-view/packs-home) are the only screens on the study theme, and they still mix study classes with shadcn Button and ad-hoc Tailwind rows. One verified layout bug comes from the byte-copied theme: .study-bar is sticky at top:0 with z-index 5, while the app header in layout.tsx:35 is also sticky top-0 at z-50. The exam clock bar therefore slides under the header when you scroll. Fleet's own rule is that --fleet-header-h (88px) is the only legal sticky offset. Recommendation: one system that keeps the current globals.css zinc tokens as the base (they already are the fleet values) and adopts the study theme (graph-paper ground, the sheet as the one card, the study tabs/choice/note/track pieces) as the look of every study screen. Wrap it in typed React components under src/kit, keep fleet-study.css as a byte-copy that is never edited locally (fix .study-bar upstream in fleet.css and re-copy), and delete the old practice/exam code along with the dead CSS.

## ?

LearnHub is a fully client-rendered Next 15.2.9 / React 19 app. Every page.tsx under src/app starts with "use client". The only server component is the root layout (src/app/layout.tsx:19-65), and it just mounts the DocumentProvider client context. Nothing fetches data on the server: all reads go from the browser through src/gateways/api/* to the /api/learn/[...path] proxy (src/app/api/learn/[...path]/route.ts:32-50) and on to FastAPI. Every gateway function follows one pattern: raw fetch(`/api/learn/...`, {cache:'no-store'}) then parseJsonResponse (src/gateways/api/http.ts:3-13). That helper throws a bare Error(message) on any non-2xx response. It keeps no HTTP status and accepts no AbortSignal. It also loses FastAPI 422 messages, because `detail` is an array there, so the user sees only the status text. A useAsyncData primitive exists (src/kit/hooks/use-async-data.ts:27-69) and its own comment says it replaced fourteen hand-rolled copies, but only 3 call sites use it (course-home.tsx:146,151 and use-course-chapters.ts:12). Roughly 40 other components still hand-roll useState+useEffect fetches in at least four idioms. The most serious problems are in the surfaces used daily. FSRS grades are fire-and-forget with errors swallowed (review-panel.tsx:69, lesson-panel.tsx:53, concept-detail.tsx:48 even shows "Recorded" on failure, pack-view.tsx:211/216). There is no stale-response guard in guided reading (use-guided-reading-data.ts:44-57), in the course syllabus tree load (use-course-data.ts:93-112), or in the pack unit load (pack-view.tsx:290-298). One exam-pack failure can strand a sitting: finishSitting at pack-view.tsx:401-406 has no try/catch, and its finishing.current ref is never reset. The documents context also has a trap. A failed first load sets isInitialized=true with an empty list and never retries (document-context.tsx:104-142), so every course route shows "Course not found". The same data is fetched independently by many components: study-debt has 4 consumers, concept-mastery 3, outline 3, mastery 2, reading-progress 3, versions 2. And nothing invalidates after a mutation, so the nav due badge (app-nav.tsx:24-33) only updates on its 5-minute poll. My recommendation is @tanstack/react-query v5 over growing useAsyncData. The app needs exactly what react-query provides: shared cache/dedup, mutation→invalidation, conditional refetchInterval, AbortSignal in queryFn, serialized mutations (`scope`), and retry. The app has no SSR data, so there is no hydration complexity. The provider drops into the existing layout next to DocumentProvider. On top of it sits a thin in-house API: an ApiError class, a query-key factory, useApi/useApiMutation wrappers, and an <AsyncView>/<ErrorNotice> pair, so every surface renders loading, error, empty and retry the same way.

### Client pattern (src/gateways/api/*)
- Base URL: hard-coded relative `/api/learn/...` in each module. Only packs.ts:146-161 has small `get`/`post` helpers. The other 15 modules repeat `fetch(...); return parseJsonResponse(res)`.
- Error shape: http.ts:3-13 throws `new Error(detail|error|statusText)`. No status code is kept, so 401 (middleware.ts returns `{error:'Unauthorized'}`), 404 and 503 can't be told apart. FastAPI 422 `detail` is an array, so it falls through to statusText.
- Return type `T & {error?: string}`: callers check `res.error`, but the backend maps every error envelope to a non-2xx (e.g. pack_routes.py:13-14, progress_routes.py:33, content_routes.py:150-151), so those branches almost never run. That is dead defensive code all over the codebase.
- Exceptions: pipeline.ts:21-34 (`fetchCourseStatus`) returns 404 as a state instead of throwing. audiobook.ts:64-78 and :90-98 swallow errors to `null` / `[]`. progress.ts:73-79 `recordEngagement` is fire-and-forget with `.catch(()=>{})`.
- Raw fetch outside the gateways: reading-progress.ts:169-193 (`/api/user-settings`, swallows errors, does a GET then PUT on every save, so two quick saves race and the last one wins), document-context.tsx:110,149 (`/api/documents`), pdf-book-view.tsx:34 (HEAD on the PDF).
- No gateway accepts an `AbortSignal`, so stale requests are ignored at best, never cancelled.
- `next.config.mjs` sets `typescript.ignoreBuildErrors: true`, so gateway typing is never enforced at build time.
- No `error.tsx` exists anywhere under src/app, so there is no error boundary for render errors.

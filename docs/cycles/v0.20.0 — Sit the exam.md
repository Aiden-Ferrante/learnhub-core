> the exam did

> Falsifier: every practice item is answerable by restating a concept's definition — the
> pool is recall wearing a problem's clothes

## Problem

The waypoint above names an exam, and the app does not have one. What it has is a practice
session: chapter-scoped, one item at a time, reveal-then-self-grade, and **you see the
worked solution the moment you ask for it**. That loop is right for spaced practice and
useless as an audit, for one reason — nothing makes you commit an answer before the
solution appears. "I knew that" is the easiest lie in studying, and the practice session
does nothing to stop it.

A real exam differs in three ways that all matter here:

1. **You write your answer first**, and only then see what a correct one looks like.
2. **It spans chapters.** Practice is scoped to one; competence is knowing which chapter a
   problem belongs to, which a single-chapter run never tests.
3. **It is a fixed set you can sit again.** A score means nothing without a comparable one,
   and every other assembly in this app is a live query that changes underneath you.

Point 3 is why this is the one assembly the spec allows to store a row. The item set has to
freeze at the start — a regeneration mid-exam must not shift the paper — answers have to
survive a reload, and a resit needs two persisted sittings to compare.

## Appetite

One sitting, and the exam is worth cutting scope for: if it overruns, the resit comparison
goes first, then the per-section breakdown. What cannot go is committing an answer before
the reveal, which is the entire reason the feature exists.

## Plan

1. **`exam_sessions`** — one row per sitting: the frozen ordered item list, a `config`, an
   `answers` map, `resit_of`, `status`, timestamps. Migration + `01-schema.sql`, applied by
   hand.
2. **`supplemental/study/exams.py`** — assemble (stratified across the chosen chapters,
   through `concept_filter` so a re-cut version inherits), answer (upsert one response),
   finish, results (total + per-section + per-kind), resit (copy the item list verbatim).
3. **Grades flow through the existing engine.** Each self-grade on the results walk calls
   `grade_review` with `{practice: true, practiceKey}`, tagged `event_kind="exam"` — so a
   sitting moves the same `prac-` FSRS rows and the same production-fluency denominator as
   practice, through one deterministic path. No second scheduler, no LLM in the loop.
4. **Three screens as a third mode** on the Practice surface — setup, runner, results.
   Never a nav tab.

**Non-goals.** No new item kinds: with only `retrieve` and `problem` in the pool, every
question is self-graded, and the objective scoring for `mcq`/`order` arrives with those
kinds rather than being written speculatively now. No proctoring, no pass/fail, no
hard timer — a countdown that locks you out of your own study app is a punishment
looking for a crime. No LLM anywhere in the graded path.

## Exit criteria

1. A sitting spanning two chapters assembles a mixed set, and **a regeneration of one of
   its sections mid-exam changes nothing** in the paper.
2. Answers survive a reload: a sitting resumes where it was left, with responses intact.
3. Finishing walks each answer beside its worked solution and rubric, self-graded 1-4.
4. A finished sitting moves the activity heatmap (`byKind.exam`) and **production
   fluency**, and moves **neither coverage nor retention** — verified live.
5. Results break down per section, so the paper says *which chapter* let you down.
6. A resit of the same paper renders against the first sitting.

## Build

**The paper freezes its QUESTIONS, not its question keys — a change made mid-build.** The
plan stored an ordered list of `ext_practice` keys, which is not a frozen paper: a
regeneration deletes unedited items, so a question could vanish from a sitting already in
progress, and a resit months later would be a different exam wearing the same name. The
sitting now snapshots prompt, worked solution, rubric, kind and section at creation. This
is the deliberate opposite of the practice session, which reads items live so an edit shows
on the next card — a card is a view of the pool, a sitting is a record of what was asked.

**Which forced a second decision: what happens when you mark an answer to a question that
no longer exists.** The FSRS row is gone, so the grade can feed nothing. Failing the whole
marking walk is wrong, and silently dropping the grade is worse. `grade_answer` asks
whether the item is still alive *before* grading and returns `scheduled: false`, the grade
is kept on your paper, and the results screen says out loud that it did not move your
schedule. Asked rather than inferred from the error code, because the resolver reports a
missing item as a 400, which is indistinguishable from a malformed request.

**One engine, one denominator.** `_TypedItem` gained an `event_kinds` allowlist so an exam
can tag its study events `kind='exam'` while grading through the identical `grade_review`
path as practice — same `prac-` rows, same FSRS, same production-fluency denominator. A
caller cannot invent a kind; only the ones the item type declares are honoured.

**Two defects the browser found that the API tests could not.**

1. **Reloading mid-paper offered you the marking screen.** The runner's position is
   component state, so a reload dropped to the setup list, where every past sitting opened
   its *results* — showing worked solutions for questions still to be answered. That is the
   one thing an exam must never do, and it defeated the feature's whole reason for
   existing. An unfinished sitting now resumes into the runner.
2. **"Closing the tab loses nothing" was false as written.** Answers saved on blur and on
   navigation, so typing a long answer and closing the tab lost it — the exact case the
   copy promised. Now debounced-autosaved 800ms after you stop typing, the same pattern the
   documents autosave uses.

**An unmarked section read "0/1"** in the breakdown, which says "you got none right" about
a question nobody has marked. Now "— of 1". Same rule as the fluency tile: an absent
measurement is never rendered as a bad one.

## Test

End to end against the real course (AI 101 — Mathematics for ML), API first and then the
whole flow through the browser.

1. **Frozen paper — the decisive test.** A 6-question sitting was created across three
   chapters, then one of its questions was **deleted from the pool** while the sitting was
   open. The paper still carried all six questions with prompt and worked solution intact.
2. **Resume.** Answers written through the UI appear in the row; the sitting reopens into
   the runner at the first unanswered question with responses restored. Autosave verified
   server-side without any blur or navigation.
3. **Answer-before-solution.** On the runner, `Worked solution` is absent from the DOM;
   after submitting, your answer renders beside it.
4. **The measurement contract, checked tightly rather than across days.** Grading fresh
   problem items through an exam: coverage `54/605 → 54/605` UNCHANGED, retention
   `0.886873 → 0.886873` UNCHANGED, production fluency `attempted 3 → 5` MOVED. (An earlier
   93.5% → 88.7% retention reading spanned two days and was FSRS decay, not the exam —
   worth stating because it looked like a regression until it was measured properly.)
   Activity heatmap gained `exam: 5`.
5. **Per-section breakdown**, live: `toc:1 1/1 · toc:1.1 — of 1 · toc:1.2 — of 1 …`, sorted
   worst-first, so the paper names the chapter rather than just the score.
6. **Resit.** Copying the paper gives the same 6 questions, answers reset, `resitOf` set,
   and the results compare `6/6 (100%)` against the prior `5/6 (83%)`.

Suite: 165 passed, 29 skipped, 1 xfailed — including new unit tests for the stratified
draw (one long section cannot crowd out a chapter) and for a score of nothing graded
reporting `fraction: None` rather than zero.

## Review

**The exam's value is a constraint, not a feature.** Everything here — the frozen paper,
the stored answers, the marking walk — exists to enforce one rule: you write your answer
before you see the solution. Both browser-found defects were failures of exactly that rule
rather than of any mechanism, and both would have passed an API-level test suite. The
feature can be entirely working and entirely pointless at the same time, which is the same
lesson v0.19.1 recorded and the reason this cycle's criteria were written as behaviours
rather than endpoints.

**Freezing content rather than references is the durable decision here.** It looks like
denormalisation and it is really about what a record means: a sitting is a historical
claim about what you were asked and how you did, and a claim that re-reads its own
evidence from a mutable source is not a record. The practice session wants the opposite
and gets it. Both are right, and writing down which is which is what keeps them from
drifting into each other.

**Not yet measured.** Competency's waypoint says the app should tell you that you cannot
work a problem *before the exam does*. Nothing here proves that — it builds the exam that
would do the telling. Whether production fluency actually anticipates a bad sitting is a
question for the first time a real paper is sat cold, and the node's sounding stays
`assumed` until then.

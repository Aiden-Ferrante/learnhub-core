# v0.25.1 — Retire practice data

Light cycle under [[0.) Development Protocol 1.0]]
Opened 2026-11-03

Addresses **Make learning more efficient**

> Each of fidelity, retention, competency and engagement carries evidence from one real book I studied end to end — not a demo corpus, and not the same book for all four

## Problem

v0.25.0 removed the old practice session and old exam mode from the UI but left their
backend and stored rows (Backlog: "Dead backend"). The human's call, 2026-11-03: "delete the
old practice data with a migration". Opened although 'Competency' holds the focus, on that
direct ask, as with v0.25.0.

## Appetite

An hour of agent time.

## Plan

One migration that removes the practice data and tables, plus the backend code that reads
them, so nothing can query a dropped table or regenerate the pool.

On prod before the change (read-only count, 2026-11-03): `ext_practice` 163 rows (0 hand-edited,
two books: 137 + 26), `exam_sessions` 0, `concept_reviews` prac- rows 0, study events keyed
prac- 0, `chapter_builds` kind practice 2.

**Non-goals.** Pack data. Pack `pack-*` reviews stay, and pack Learn grades keep logging study
event kind `practice` (packs.py), so no event is deleted by kind. The 6 `exam` events of
2026-11-03 are the PE1 Operators pack sitting and stay. Historical docs (practice-items-spec,
ui-inventory) stay as written.

## Exit criteria

- `ext_practice` and `exam_sessions` do not exist on prod; no prac- reviews or practice jobs remain.
- Pack rows unchanged: 6 `pack-*` reviews, 6 `exam` events.
- The rebuilt backend serves `/health` 200, `/api/exams` 404, and study-debt / packs as before.
- pytest passes.

## Build

- Backup before anything: `~/Documents/backups/learnhub/2026-11-03-practice-before-drop.sql`
  (163 ext_practice rows, data-only) and `2026-11-03-practice-builds.tsv` (2 jobs).
- Removed: `api/practice_routes.py`, `supplemental/study/exams.py`,
  `process/extraction/practice.py` and `practice_checks.py`, their schemas and tests, the
  `practice` build runner and ledger kind, the prac- typed review item and the
  `session=practice` queue, and the Fluency read model in mastery.py.
- `_author_model` / `_judge_model` moved into `process/packs/author.py`, keeping the
  `LEARN_PRACTICE_*` env names so the deployed config still applies.
- Migration `deploy/postgres/migrations/2026-11-03-retire-practice.sql`, mirrored by removing
  both tables from `init/01-schema.sql`.
- **Blocked for the agent:** a local hook refuses DROP/DELETE SQL, and the permission layer
  refused the prod image rebuild. The human runs both.

## Test

- pytest: 182 passed, 30 skipped, 1 xfailed (48 practice/exam tests deleted with their code).
- `import app.main` clean.
Prod, 2026-11-04, after the human ran the migration and the restart (the agent built the image):
- Both tables are gone (`information_schema` count 0). There are 0 prac- reviews and 0 practice
  jobs. The 6 `pack-*` reviews and 6 `exam` events are still there.
- `/health` 200, `/api/exams` 404, `/api/practice` 404, study-debt `dueNow` 11 (same as
  before), `/api/packs` 200, mastery 200, course review queue 200, UI `/login` 200, and no
  errors in the backend log.
- **Miss:** between the migration and the restart, the old image answered `/api/exams` with
  500 (dropped table). Nothing in the UI calls it. The first rebuild the human ran never
  happened (no new image), so the build was split: the agent built and the human ran `up -d`.

## Review

**What did the plan miss?** That the deploy order would be split across two people. Rebuild
first, then migrate, was the safe order. The rebuild did not land the first time, so for a
while old code ran against the new schema.

**What did the agent need that the prompt did not give?** That pack Learn grades log event kind
`practice`. Deleting events by kind would have erased pack history. The ui-inventory flagged
it, and the delete keys on `prac-` instead.

**What did I learn?** An image build is allowed for the agent, but `up -d` on prod is not. Hand
the human exactly that one command, with `!`, so its output lands in the session.

Decision: ship.

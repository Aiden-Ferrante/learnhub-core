# v0.23.0 — Set the paper

Sub-cycle plan under [[0.) Development Protocol 1.0]]
Opened 2026-09-08

Addresses **Competency**

> Each of item pool and production fluency holds on a real book: a chapter yields problems worth sitting down to, and the app tells me I cannot work one before the exam does

## Problem

The exam setup lists top-level chapters only, shows nothing about which of them have items,
and says "no practice items yet" only after Start. The learner cannot pick sections, cannot
tell what is processed, cannot choose kinds even though the backend already filters on
them, and cannot ask for easier or harder questions because an item has no difficulty at
all. Every one of those is a decision the learner should be making about their own paper.

What is at stake: the deployed app (:3001) has NEVER run practice or exams — 0 rows in
`ext_practice`, 10 study events total. Every v0.19.0–v0.20.0 criterion was observed on the
dev clone (:5433), chapter 1 of one book. The Competency nodes are all `assumed`. A paper
the learner cannot shape is a paper nobody sits, and nothing gets measured.

**Decided by the human, 2026-09-08 (anchored on Competency):** generation stays ONE
CHAPTER AT A TIME from the editor — a whole-book generate was proposed and rejected. The
flexibility belongs in the pick, not in generation. The paper is fully user-set: question
count per picked chapter or section, kinds, and difficulty on a 1–3 scale.

## Appetite

Two sittings of build plus one real paper sat by the human. Shed order if it overruns: the
editor's re-rate select (ratings stay generation-only), then section-level picks (keep
chapter-level with counts). What cannot go: per-pick count, kinds and difficulty filters,
only processed scopes pickable, and a pick that is honest about the draw.

## Plan

0. **Difficulty on the item.** `ext_practice.difficulty smallint CHECK (1..3)` — migration
   `2026-09-08-practice-difficulty.sql` + `init/01-schema.sql`, applied by hand. The
   authoring schemas gain `difficulty`; both prompts define the scale (1 = applies one
   definition or rule directly · 2 = combines several steps or two ideas · 3 = constructs,
   proves, or is multi-part) and ask for a spread. Out-of-range ratings are stored NULL,
   never coerced. `difficulty` joins `EDITABLE_FIELDS`; the Practice tab shows it as an
   editable select. NULL renders "—" and is drawn only when no difficulty filter is set.
   Prod has 0 items, so there is nothing to backfill.
1. **Pool read before the pick.** `GET /api/exams/pool?doc=` — per version-section counts
   by kind × difficulty, read through `concept_filter` like every other pool read. Zero
   means unprocessed. The frontend rolls sections up into chapters from the tree it has.
2. **Setup screen is the outline.** Chapters expand to sections; a chapter pick takes all
   its sections, a section pick takes that one. Zero-count nodes are greyed "not generated
   yet" and unpickable. Each picked row carries its own count, clamped to what is available
   under the current filters. Global kinds checkboxes (retrieve · problem; mcq/order/code
   greyed "not built") and a difficulty multi-select. The footer states the real draw.
3. **The draw honours the pick.** `create_exam(picks=[{scope,count}], kinds, difficulties)`
   filters the pool on both, stratifies within each pick as today, freezes the paper, and
   stores the whole pick in `config`. Legacy `{chapters, perChapter}` bodies still work and
   old rows still render. Snapshot, marking, results, resit are untouched.

**Non-goals.** No whole-book generation (anchored). No `mcq`/`order`/`code` kinds and no
runner. No auto-grading. No fluency-before snapshot on a sitting — carried to Backlog. No
new table. No LLM anywhere in the graded path.

## Exit criteria (observed on :3001, images rebuilt, migration applied)

1. A regenerated chapter of *AI 101 §3 — Programming for ML* carries ratings the reader
   agrees with on reading, or is re-rated and the re-rating survives the next regeneration.
2. With two generated chapters of many: exactly two pickable; ungenerated sibling sections
   greyed inside them.
3. A paper set as "chapter A, all sections, 6 · section B.x, 3 · problems only · difficulty
   2–3" draws exactly 9 items, all problems, none rated 1, all from those spans — read from
   the frozen `items` JSON.
4. Asking for more than a node holds clamps and says so BEFORE Start, not after.
5. Coverage and retention unchanged after marking; fluency moved — re-checked on prod.
6. One self-set paper sat by the human; every miss logged here.

## Build

_2026-09-08, first sitting._ Backend then frontend, two commits per the plan's rungs
(difficulty · pick-based draw · the outline setup). Decisions taken on the way:

- **Out-of-range ratings are unrated, not clamped.** The schema asks for an int and the
  model can answer 0 or 7; clamping either to 1 or 3 would mint a confident number nobody
  chose. `_rating` returns None outside 1..3, at generation and on edit alike (an edit with
  a bad value is refused with a sentence rather than silently unrated).
- **A difficulty filter excludes unrated items.** "2–3" means rated 2 or 3. Promoting an
  unrated item into a filtered draw would be the same absent-measurement-as-a-number
  failure the fluency tile exists to avoid. The setup screen says so beside the filter.
- **`count: 0` is not "default".** First cut read `int(raw or DEFAULT)`, so an explicit 0
  became 5 — a request for nothing silently became a request for five. Now only a missing
  count takes the default; 0 clamps to 1 like any other under-range value. Caught by the
  unit test, not by reading.
- **`_pool` keeps the tag name `chapter` for a pick that may be a section.** Renaming it
  would have touched every stratify test for a word; the docstring says what it means.
- **A chapter pick covers its sections.** Picking a chapter drops any section picks inside
  it and greys those rows as "covered", so the same item can never be counted under two
  picks (the backend dedupes too — first pick wins — but the screen should not offer what
  the draw will discard).
- **The three unbuilt kinds stay visible, greyed.** A five-item list with three disabled is
  the honest shape of the pool; a two-item list would read as complete.
- **Legacy shape kept on both sides.** `config` stores `picks` AND the old `chapters` /
  `perChapter`, so the sittings already on the dev clone still list; the route accepts
  either body.

**Unbuilt on purpose at this checkpoint:** live verification. Every read of `ext_practice`
now names `difficulty`, so the backend will not serve until the column exists — DDL is
guard-blocked for agents, on the dev clone (:5433) as much as on prod. The migration is the
human's step (`deploy/postgres/migrations/2026-09-08-practice-difficulty.sql`), then the
image rebuild (`learn` and `app`).

## Test

_2026-09-09. The human applied `2026-09-08-practice-difficulty.sql` and rebuilt `learn` +
`app` (images 12:24 EDT), then generated chapters 2 and 3 of *AI 101 §3* from the editor,
one at a time. The verify rung ran against :3001 (learn on :8010) at 20:33 EDT; the session

**Rung 1 — unit.** `pytest tests/test_exams.py tests/test_practice.py`: 30 passed.

**Rung 2 — verify, observed on prod.**

- Pool (`GET /api/exams/pool?doc=b7df152c…`): 105 items across 60 sections, all under
  `toc:2` and `toc:3`; the document has 208 sections. Both kinds carry a 1–3 spread
  (chapter 2: 22 leaf + 7 chapter-level problems, 22 + 6 retrieve).
- **Criterion 3 — the pick is honoured.** Sitting `710bf83c`, config
  `picks=[{toc:2, 6}, {toc:3.3, 3}] · kinds=[problem] · difficulties=[2,3]` froze exactly
  9 items: sectionKeys `toc:2, 2.1, 2.1.1, 2.1.2, 2.1.3, 2.2` (6) and
  `toc:3.3, 3.3.1, 3.3.3` (3); all `problem`; difficulties 3,2,2,2,2,2,2,2,2 — no 1, no
  unrated. Read from the frozen `items` JSON, not the UI.
- **Criterion 4 — clamping.** Backend: `{toc:2, 60, difficulties=[1]}` drew 16 (every
  rated-1 item under chapter 2, and only those); `{toc:3.3, 50, kinds=[retrieve]}` drew 4.
  Screen: the count input carries `max = available under the current filters` and the
  footer states the real draw, so the clamp is visible before Start. The *before Start*
  half is a UI claim and is left to first contact — the agent cannot log in to :3001
  (password entry is the human's).
- **Criterion 2 — only processed nodes pickable.** Backend side: every section outside
  chapters 2 and 3 reads zero in the pool. Screen side (`exam-mode.tsx` row: `disabled
  when n === 0 || covered`, label "not generated yet") is left to first contact.
- **Criterion 5 — the axes.** After `finish` + two `grade` calls on `710bf83c`:
  `study_events` gained exactly two `exam` rows (toc:2 correct, toc:2.1 incorrect);
  no `read`/`review` rows were added, so coverage (6/161 = 0.037) and retention (0.91)
  are unchanged by construction. Overall fluency moved from `unattempted` to
  `measured`, attempted 2 of 56.
- Legacy shape: `config` stores both `picks` and `chapters`/`perChapter`; `GET /api/exams`
  lists the four sittings without error.

**Misses found by reading the real artifact, both outside this cycle's scope:**

- *M1 — per-section fluency drops chapter-level items.* `/api/mastery` reports chapter 2
  fluency over 22 items and `attempted 0`, while the pool holds 29 problems under it and
  the two graded items (`toc:2`, `toc:2.1`) were attempted. The rollup in `mastery.py`
  sums `descendant_leaves` only, so an item (or a concept) attached to a non-leaf section
  is invisible to every per-section number; overall (56, attempted 2) is right because it
  skips the tree. Latent since v0.19.0; the earlier book put no prose on chapter nodes, this
  one does. Carried to Backlog.
- *M2 — fluency reads 1.0 with a 50% paper.* One good and one poor self-grade, and
  overall fluency is 1.00: FSRS retrievability is ~1 the moment after any review, whatever
  the grade. The number is honest about the engine and useless about the sitting. A
  question for the retro, not a fix.

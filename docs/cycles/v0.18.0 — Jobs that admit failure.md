## Problem

The queue's failures are invisible. A job can die, double-run, or refuse to stop, and every
surface above it renders a confident status.

- **C1** Terminal ledger writes are best-effort — including the `running` claim. Losing that
  write re-hands the same row to the next poll: a silent double-run.
- **C2** Not every exit from `run_convert` marks the document, so a broken import keeps
  squatting on its content hash and the next upload of the same book dedups onto a corpse.
- **C3** An extraction where *every* section failed still reports success.
- **C4** Skeleton caches empty essences at the current prompt version, so a failed generation
  is remembered as a real (empty) answer.
- **C5** Interrupted jobs have no attempt cap and no backoff — the `not_before` column
  already exists and `next_job` already honours it, so this is wiring, not design.
- **C6** Cancel does not fire. The runners that never call `ctx.progress` never reach a
  cancel check, so the flag is set and nothing reads it.
- **D1–D7** The splitter: fenced code blocks, setext headings, duplicate-heading collisions.

## Appetite

One sub-cycle. C1–C5 are ledger discipline and small; C6 has a cheap half and an expensive
half, and only the cheap half is in scope (see Plan). If the expensive half starts looking
necessary to close the cycle, that is the re-plan valve firing.

## Plan

C1–C5 as listed. C6 **the cheap half only**: make cancel reachable in the runners that never
call `ctx.progress`, plus honest UI copy about what cancel can and cannot stop.

Splitter work D1–D7 rides along; **D7 (duplicate-heading collisions) already landed** in
`6a54ae6`, ahead of this cycle opening.

**Non-goals.** Real mid-flight convert cancel: docling is a single opaque call with no page
loop to hook, so interrupting it means hosting the engine in a killable subprocess. Deferred
as a design change, not a bug fix. Incremental concept writes are likewise deferred — they
change the dedup's first-occurrence semantics.

## Exit criteria

1. A job that dies mid-run is not silently re-handed to the next poll.
2. A convert that fails by any path leaves the document marked, and the next upload of the
   same book is not deduped onto it.
3. An extraction where every section failed reports failure.
4. Cancel stops a queued job immediately, and a cancelled long job does not persist its
   output — and the UI says which of those two happened rather than implying the first.
5. Cancel-then-restart actually stops the job. Today it is the *only* way to stop an
   uninterruptible convert, and it makes it worse.
6. Per the standing rule, **render the real artifact**: cancel a real conversion in the
   running app with the images rebuilt. Every one of these produces a plausible status
   string, so a fixture suite cannot close any of them.

## Build

_Filled in as it happens: decisions taken, and why._

**Landed so far — the C6 cheap half, plus one C1-adjacent fix.**

`conductor/ingest.py` — two `ctx.check_cancel()` calls now bracket the engine in
`run_convert`. Recorded plainly in the code and repeated here because it is the limit of what
this cycle buys: **they bracket the engine, they do not interrupt it.** `convert_document()`
is a single opaque call into docling with no page loop to hook, so a conversion already
inside the engine runs to completion. What the brackets do buy, and it is most of the value:
a job cancelled while queued or in the window before the engine starts stops immediately, and
a job cancelled *during* a long conversion does not then persist a document nobody wants. The
pages are already spent; the point is that the library does not gain a book you asked it to
abandon. Before this the convert runner never called `check_cancel` at all — only
`ctx.progress()` reaches it, and convert has no per-item loop to report progress against, so
`cancel` on a convert set a flag nothing ever read.

`gateways/ledger.py` — `requeue_interrupted()` now settles a job whose cancel was requested as
`canceled` instead of requeueing it. This is exit criterion 5 and it is the sharper half of
the fix: restarting the service was the only way to stop work the engine cannot interrupt,
and the restart promptly requeued the very job you were trying to kill, from the top. Cancel
then restart now actually stops it, which is the sequence a user reaches for.

Also already landed, ahead of this record: `2864732` (let a running job be stopped, and name
the kind that is running), `37815b4` (whole-document jobs cancellable), `6a54ae6` (D7).

**C1 — the double-run is closed at the source.** `next_job` was a bare SELECT, with the
worker marking the row `running` afterwards through a write that swallowed every error: lose
that write and the row stays queued, the next poll hands out the same job, and the same
conversion runs twice with nothing saying so. Selection and claim are now one statement
(`UPDATE … WHERE key = (SELECT … FOR UPDATE SKIP LOCKED) RETURNING *`), which removes the
failure mode rather than narrowing it. The worker's own "mark it running" write is gone.

Terminal writes stopped being best-effort, but only terminal ones — `status`, `finishedAt`,
`error`, `cancelRequested` raise; `phase` and progress counts stay quiet. A dropped `done`
displays a finished job as running forever; a dropped `phase` costs nothing.

**C2 — every exit from `run_convert` marks the document.** Three did not: the missing-file
return, a cancel, and any unanticipated exception. All three left the stub at `converting`
— permanently mid-flight, invisible to the shelf, still holding its content hash so
re-uploading the same book deduped onto the corpse. **The dev library had two of these**,
from 2026-07-22 and 2026-08-22.

**C3 — an extraction where every section failed reports failure.** `extract_concepts_document`
sets `error` only when the run cannot start, so a chapter whose every section failed arrived
as a clean `done` with zero concepts — indistinguishable from a chapter that teaches nothing.
Partial failure still succeeds; that boundary is what keeps the rule useful.

**C4 — an empty skeleton is not cached.** When the model call fails, every essence is the
empty string and the result looks well-formed: right shape, right order, right headings, no
content. Caching it stamps the current prompt version, which is exactly what the lazy
regenerate keys on, so one failed call became that chapter's permanent skeleton.

**C5 — interrupted jobs are capped and backed off.** `requeue_interrupted` counts attempts
and sets `not_before` to an exponential backoff; past `MAX_ATTEMPTS` the job is settled as
`error` instead of requeued. The worker is single-threaded, so an uncapped crash-requeue loop
does not retry one job — it stops every other job from ever running.

**D1 — a `#` inside a fenced code block is a comment, not a heading.** It opened a section,
chopping the block mid-listing and feeding extraction half a code sample under a heading the
author never wrote. **11 of the library's 12 books contain fenced code.** The fence rule
tracks the fence character and length, so a ``` block containing ~~~ is not closed by it.

**D2 — setext headings are read.** A title underlined by `===` or `---` had no handling at
all, so it became body text of the preceding section and a real chapter vanished from the
outline. Guarded against horizontal rules, table separators and list items.

**One regression, introduced by this cycle's own fix and caught before it shipped.** Making
`requeue_interrupted` raise was right at the gateway; the worker calls it *outside* its loop,
so the raise would have killed the worker thread for the life of the process — the queue
silently draining nothing, which is precisely the failure this cycle exists to remove. The
worker catches and logs it deliberately, and a test pins that the loop is still entered.

**Not built:** D3–D6. No splitter finding beyond fenced code and setext headings was
exercised by a real book in the library, so they go to `Backlog.md` rather than being written
blind.

## Test

_What was actually run, and what it said._

Nothing yet beyond the existing suite (151 passed, 1 xfailed, 2026-08-25). No test covers
the cancel paths.

Exit criteria 4, 5 and 6 all require cancelling a real conversion in the running app and
have not been run — which matters more here than the count does, because both landed changes
are about what happens to a job nobody is watching. Criterion 5 in particular (cancel, then
restart, and the job stays dead) cannot be observed any other way.

## Review

_Filled in at the gate, 2026-08-26. **Closed.**_

**The cycle's best moment was its own regression.** Making the recovery write raise instead of
`pass` is straightforwardly right, and it would have killed the worker on the first failed
recovery because the call sits outside the loop. An honesty fix that silently stops the queue
is worse than the dishonesty it replaced. It was caught by running the thing, not by reading
it — the same lesson v0.16.0 recorded about probes, arriving from the other direction.

**What carries forward** (→ `Backlog.md`):

- D3–D6 were not built. Nothing in the library exercised them, and writing splitter rules
  against imagined markdown is how the fenced-code bug got missed in the first place.
- `run_convert`'s failure paths are unexercised. A fault-injection hook for the converter
  would make criterion 2 checkable rather than argued.
- The ledger key includes `kind`, and `build`/`extract` are runner aliases but not key
  aliases. Nothing is broken, but the asymmetry cost twenty minutes and will again.

Carried in from [[v0.15.0 — Say what you did]]'s review: `37815b4` overlaps C6 and predates
this record, so part of this cycle was built before it was opened. That is the failure mode
this record exists to stop — work landing against a cycle number that only lives in a
fossilised prose reservation, invisible to `repo.cycle_records()` until someone writes the
file.

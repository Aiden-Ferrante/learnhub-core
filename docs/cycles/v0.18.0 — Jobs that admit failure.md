## Problem

The queue's failures are invisible. A job can die, double-run, or refuse to stop, and every
surface above it renders a confident status.

- **C1** Terminal ledger writes are best-effort — including the `running` claim. Losing that
  write re-hands the same row to the next poll: a silent double-run.
- **C2** Not every exit from `run_convert` marks the document, so a broken import keeps
  squatting on its content hash and the next upload of the same book dedups onto a corpse.
- **C3** An extraction where *every* section failed still reports success.
- **C4** Skeleton caches empty essences at the current prompt version, so a failed generation
  is remembered as a real (empty) answer.
- **C5** Interrupted jobs have no attempt cap and no backoff — the `not_before` column
  already exists and `next_job` already honours it, so this is wiring, not design.
- **C6** Cancel does not fire. The runners that never call `ctx.progress` never reach a
  cancel check, so the flag is set and nothing reads it.
- **D1–D7** The splitter: fenced code blocks, setext headings, duplicate-heading collisions.

## Appetite

One sub-cycle. C1–C5 are ledger discipline and small; C6 has a cheap half and an expensive
half, and only the cheap half is in scope (see Plan). If the expensive half starts looking
necessary to close the cycle, that is the re-plan valve firing.

## Plan

C1–C5 as listed. C6 **the cheap half only**: make cancel reachable in the runners that never
call `ctx.progress`, plus honest UI copy about what cancel can and cannot stop.

Splitter work D1–D7 rides along; **D7 (duplicate-heading collisions) already landed** in
`6a54ae6`, ahead of this cycle opening.

**Non-goals.** Real mid-flight convert cancel: docling is a single opaque call with no page
loop to hook, so interrupting it means hosting the engine in a killable subprocess. Deferred
as a design change, not a bug fix. Incremental concept writes are likewise deferred — they
change the dedup's first-occurrence semantics.

## Exit criteria

1. A job that dies mid-run is not silently re-handed to the next poll.
2. A convert that fails by any path leaves the document marked, and the next upload of the
   same book is not deduped onto it.
3. An extraction where every section failed reports failure.
4. Cancel stops a queued job immediately, and a cancelled long job does not persist its
   output — and the UI says which of those two happened rather than implying the first.
5. Cancel-then-restart actually stops the job. Today it is the *only* way to stop an
   uninterruptible convert, and it makes it worse.
6. Per the standing rule, **render the real artifact**: cancel a real conversion in the
   running app with the images rebuilt. Every one of these produces a plausible status
   string, so a fixture suite cannot close any of them.

## Build

_Filled in as it happens: decisions taken, and why._

**Landed so far — the C6 cheap half, plus one C1-adjacent fix.**

`conductor/ingest.py` — two `ctx.check_cancel()` calls now bracket the engine in
`run_convert`. Recorded plainly in the code and repeated here because it is the limit of what
this cycle buys: **they bracket the engine, they do not interrupt it.** `convert_document()`
is a single opaque call into docling with no page loop to hook, so a conversion already
inside the engine runs to completion. What the brackets do buy, and it is most of the value:
a job cancelled while queued or in the window before the engine starts stops immediately, and
a job cancelled *during* a long conversion does not then persist a document nobody wants. The
pages are already spent; the point is that the library does not gain a book you asked it to
abandon. Before this the convert runner never called `check_cancel` at all — only
`ctx.progress()` reaches it, and convert has no per-item loop to report progress against, so
`cancel` on a convert set a flag nothing ever read.

`gateways/ledger.py` — `requeue_interrupted()` now settles a job whose cancel was requested as
`canceled` instead of requeueing it. This is exit criterion 5 and it is the sharper half of
the fix: restarting the service was the only way to stop work the engine cannot interrupt,
and the restart promptly requeued the very job you were trying to kill, from the top. Cancel
then restart now actually stops it, which is the sequence a user reaches for.

Also already landed, ahead of this record: `2864732` (let a running job be stopped, and name
the kind that is running), `37815b4` (whole-document jobs cancellable), `6a54ae6` (D7).

**Not yet built:** C1 proper, C2, C3, C4, C5, D1–D6, and tests for any of it. This cycle is
open.

## Test

_What was actually run, and what it said._

Nothing yet beyond the existing suite (151 passed, 1 xfailed, 2026-08-25). No test covers
the cancel paths.

Exit criteria 4, 5 and 6 all require cancelling a real conversion in the running app and
have not been run — which matters more here than the count does, because both landed changes
are about what happens to a job nobody is watching. Criterion 5 in particular (cancel, then
restart, and the job stays dead) cannot be observed any other way.

## Problem

Deleting a book does not reliably delete it, and it does not reliably *say* when it hasn't.

The findings, from the 2026-08-21/22 audit:

- **B1** The Processing tab's delete is a no-op that toasts success. The shelf already has
  the correct pattern; this surface never adopted it.
- **B2** `delete_document` is not transactional — a failure part-way leaves a half-deleted
  book with no error.
- **B3** The 404 check sits *below* the `rmtree`, so the files go and then the call reports
  "not found".
- **B4/B6** Re-convert's cascade, and a figure `rmtree` that runs before the transaction.
- **B5** Audiobooks are never removed. `content` may not import `media` (the layering
  forbids it), so this composes at the `api` layer via a `media` facade export.
- **B7** `origin` has no CHECK constraint — one typo stands between you and every concept
  in a book.
- **B8** Study pruning swallows errors with `except: continue`. The guard has to differ per
  function: `versions.py:175` runs inside a transaction, so catching there leaves it already
  poisoned; a `to_regclass` precheck is the right shape.
- **F4/F5** Version delete has no confirm, and the shelf dialog does not name the sibling
  versions it destroys.

The delete paths have **zero** test coverage today.

## Appetite

One sub-cycle. This is a repair pass over one function and its two call sites plus a schema
constraint — if it starts growing a delete *subsystem*, abort and re-plan.

## Plan

Work B1–B8 and F4/F5 as listed above, then cover the delete paths with tests.

**Amendment to B3, taken during build.** B3 says move the 404 above the `rmtree`. That keeps
a 404 for an absent document, and it is wrong — see Build below. `DELETE` is idempotent: an
absent document is success. B3 is superseded by "remove the 404", and the ordering problem it
described disappears with it.

**Non-goals.** No job-queue work (that is v0.18.0). No splitter work. Disclosure only for
F4/F5 — *what* delete removes does not change, only what the dialog tells you it will.

## Exit criteria

1. Deleting from the Processing tab removes the document, and a failure says so.
2. `delete_document` is atomic: it either removes the whole `raw_`/`ext_` graph, its jobs,
   its files and its audiobooks, or it changes nothing and reports the failure.
3. A delete of an already-absent document succeeds, and the orphan card disappears from the
   shelf.
4. `origin` rejects an unknown value at the database, not in application convention.
5. The delete paths have tests — they have none today.
6. Per the standing rule, **render the real artifact**: delete a real book in the running
   app with the images rebuilt, and confirm the rows, the files and the card are all gone.
   A green suite over fixtures cannot see an orphaned directory.

## Build

_Filled in as it happens: decisions taken, and why._

**Landed so far — the idempotent DELETE only** (`process/content/documents.py`).

`delete_document` returned `{"error": "document … not found", "status": 404}` when neither a
row nor files existed. That made an orphan shelf card **permanently undeletable from the UI**:
the card lives in `app_documents`, written by the browser, and the client only prunes it after
the backend call succeeds. A card whose backing document had already been removed failed its
own delete forever, and the only way out was SQL.

So the 404 is gone and the response carries `alreadyGone` instead. The reasoning, recorded
because it amends the plan: the caller asked for this document to be gone, and it is gone.
Whether its backing row still exists is an implementation detail they cannot see, and the card
is the thing they are pointing at.

**Not yet built:** B1, B2, B4–B8, F4/F5, and the tests. This cycle is open.

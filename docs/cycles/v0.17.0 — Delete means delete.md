## Problem

Deleting a book does not reliably delete it, and it does not reliably *say* when it hasn't.

The findings, from the 2026-08-21/22 audit:

- **B1** The Processing tab's delete is a no-op that toasts success. The shelf already has
  the correct pattern; this surface never adopted it.
- **B2** `delete_document` is not transactional — a failure part-way leaves a half-deleted
  book with no error.
- **B3** The 404 check sits *below* the `rmtree`, so the files go and then the call reports
  "not found".
- **B4/B6** Re-convert's cascade, and a figure `rmtree` that runs before the transaction.
- **B5** Audiobooks are never removed. `content` may not import `media` (the layering
  forbids it), so this composes at the `api` layer via a `media` facade export.
- **B7** `origin` has no CHECK constraint — one typo stands between you and every concept
  in a book.
- **B8** Study pruning swallows errors with `except: continue`. The guard has to differ per
  function: `versions.py:175` runs inside a transaction, so catching there leaves it already
  poisoned; a `to_regclass` precheck is the right shape.
- **F4/F5** Version delete has no confirm, and the shelf dialog does not name the sibling
  versions it destroys.

The delete paths have **zero** test coverage today.

## Appetite

One sub-cycle. This is a repair pass over one function and its two call sites plus a schema
constraint — if it starts growing a delete *subsystem*, abort and re-plan.

## Plan

Work B1–B8 and F4/F5 as listed above, then cover the delete paths with tests.

**Amendment to B3, taken during build.** B3 says move the 404 above the `rmtree`. That keeps
a 404 for an absent document, and it is wrong — see Build below. `DELETE` is idempotent: an
absent document is success. B3 is superseded by "remove the 404", and the ordering problem it
described disappears with it.

**Non-goals.** No job-queue work (that is v0.18.0). No splitter work. Disclosure only for
F4/F5 — *what* delete removes does not change, only what the dialog tells you it will.

## Exit criteria

1. Deleting from the Processing tab removes the document, and a failure says so.
2. `delete_document` is atomic: it either removes the whole `raw_`/`ext_` graph, its jobs,
   its files and its audiobooks, or it changes nothing and reports the failure.
3. A delete of an already-absent document succeeds, and the orphan card disappears from the
   shelf.
4. `origin` rejects an unknown value at the database, not in application convention.
5. The delete paths have tests — they have none today.
6. Per the standing rule, **render the real artifact**: delete a real book in the running
   app with the images rebuilt, and confirm the rows, the files and the card are all gone.
   A green suite over fixtures cannot see an orphaned directory.

## Build

_Filled in as it happens: decisions taken, and why._

**Landed so far — the idempotent DELETE only** (`process/content/documents.py`).

`delete_document` returned `{"error": "document … not found", "status": 404}` when neither a
row nor files existed. That made an orphan shelf card **permanently undeletable from the UI**:
the card lives in `app_documents`, written by the browser, and the client only prunes it after
the backend call succeeds. A card whose backing document had already been removed failed its
own delete forever, and the only way out was SQL.

So the 404 is gone and the response carries `alreadyGone` instead. The reasoning, recorded
because it amends the plan: the caller asked for this document to be gone, and it is gone.
Whether its backing row still exists is an implementation detail they cannot see, and the card
is the thing they are pointing at.

**B1 — the Processing tab deletes the book, not the row.** It was a one-line array filter
that toasted success: the row vanished, the book stayed on disk with all its rows, and
nothing said so. It now calls the backend per card and prunes only what actually went; a card
whose delete failed stays on screen and stays selected, because that card is the thing you
point at to try again. The shelf has always done this correctly and was the model.

**B2 — `delete_document` runs in one transaction**, and B6 with it: files come off disk only
after the commit. The other order destroys a book's PDF and figures even when the database
work rolls back.

**B8 — the `except: continue` is gone, from both delete paths.** Both run inside a
transaction, where that shape is worse than useless: the first failure poisons the
transaction, every later statement fails too, and the `continue` hides all of them — a delete
that removed nothing would report success. `_existing_tables` asks the catalogue once, up
front, so a real error can be a real error.

That helper had a bug of its own on the first attempt: `unnest()` in a `WHERE` clause, which
Postgres refuses outright. It would have broken **every** delete, and the new tests caught it
on their first run — which is the entire argument for exit criterion 5.

**B5 — audiobooks are removed**, composed at the `api` layer via a `remove_audiobooks` export
from the media facade, because `process/content` may not import `supplemental/media`.
`delete_document` takes an `on_deleted` callback instead of an import, and it fires after the
commit.

**B4 — a re-convert no longer strands unanchored concepts.** Concepts anchored to a node go
with the tree via the FK cascade; the schema deliberately allows `structure_id IS NULL` for
concepts finer-grained than the TOC, and those survived with a `section_key` naming a section
that may no longer exist — unreachable by every scope query while still counting toward
coverage denominators.

**B7 — `origin` is constrained in `01-schema.sql`**, with
`deploy/postgres/migrations/2026-08-25-origin-check.sql` for existing databases. The
migration repairs before it constrains, and is idempotent. **It has not been applied to the
dev database** — see Test.

**F4 — deleting a course takes two clicks.** It destroys that course's outline and everything
studied against it, and sat behind one unguarded click in a dropdown, next to the row that
merely *switches* course. The button arms rather than opening a dialog, which is proportionate
to the surrounding menu, and disarms whenever the menu closes.

**F5 — the shelf dialog names the sibling courses it destroys.** Deleting a book takes every
course cut from it; the card shows one name, so the dialog was silently understating what it
was about to do. The list loads when the dialog opens and fails to empty rather than blocking
the delete — an unavailable list is a reason to say less, not to stop someone removing a book.

**Not built:** nothing from the finding list. The cycle is still open on B7's migration.

## Test

_What was actually run, and what it said._

**All six exit criteria pass.**

**Criterion 5 (tests).** `tests/test_delete_pg.py`, nine integration tests against a real
Postgres: the whole book goes including every course cut from it, the un-FK'd study tables
are reached, **another book is untouched** (the assertion that makes the rest mean anything),
an absent book succeeds, a malformed id is still refused, the callback receives every version
and runs only after the rows are gone, one course can be deleted without the book, and the
Default course cannot. They found the `unnest`-in-`WHERE` bug immediately.

**Criterion 6 (render the real artifact).** Images rebuilt, then a throwaway book ingested
through the running app and deleted through it — deliberately not one of the library's real
books. Before: 1 source, 1 version, 3 blocks, 3 structure nodes, 1 job, an ingest directory,
and a seeded audiobook directory. After the `DELETE`: **every count zero, both directories
gone**, HTTP 200. The library's own 14 documents, 56 reviews and 82 events were unchanged.

**Criterion 4 (`origin` CHECK) — PASS.** The migration was applied by hand on 2026-08-26
(`ALTER` is blocked for the agent by a `PreToolUse` guard, correctly). Demonstrated rather
than assumed: `UPDATE … SET origin='Default'` is now rejected by
`raw_documents_origin_check`, and `'default'` is still accepted.

**Exit criteria 1 and 3 — PASS, in the browser, 2026-08-26.** A throwaway book was ingested
with a real card and deleted from the Processing tab by hand. Sources, documents and cards all
went 15 → 14; its blocks, its job rows and its ingest directory all gone; 56 reviews, 82 events
and 1,463 concepts untouched.

**This took two attempts, and the first one is the finding.** The first report was that a
document had been deleted and stayed gone — which was true, and proved nothing. The Processing
tab lists `app_documents`, the browser's own cards, not backend documents; the counts had not
moved. A card carrying no `learnDocId` is pruned client-side without the backend ever being
called, so it disappears honestly and exercises none of this cycle's work. The check only
became a check once it was arranged so a *specific number had to move*.

That is the whole argument for a browser criterion existing separately from an API test. The
API half had passed for a day.

**Exit criterion 3 (backend half) — verified 2026-08-25.** Deleting a document that
was already gone returns **HTTP 200** with `{"deleted": …, "removed": {}, "alreadyGone": true}`
instead of the old 404. A malformed id still returns 400, which is correct and deliberate:
an absent resource is success, a nonsense request is not.

This was run in passing while closing v0.15.0 — a version created for that check was deleted
twice — and went unrecorded here for a day. Noted because it is the failure mode this repo
keeps finding: work that happened and was not written down reads later as work that did not
happen.

Suite: **160 passed, 1 xfailed**. Hub contract holds. Frontend `tsc --noEmit` clean.

**Not run:** the browser half of criteria 1 and 3. `:3001` sits behind a login wall, so the
Processing tab's delete and the orphan card's disappearance have been verified as far as the
API and no further.

## Review

_Filled in at the gate, 2026-08-26. **Closed.**_

**Two things nearly went out wrong, and both were caught by running rather than reading.**

The first was in the fix itself. `_existing_tables`, written to replace the `except: continue`
that poisoned its own transaction, used `unnest()` in a `WHERE` clause — which Postgres
refuses outright. It would have broken **every** delete, and the new tests caught it on their
first run. The delete paths had zero coverage before this cycle; that is what criterion 5 was
for, and it earned itself immediately.

The second was in the verification. A browser check was reported as passing, and it was: a
card was deleted and stayed deleted. It exercised nothing, because the Processing tab lists
the browser's own cards and a card with no `learnDocId` never reaches the backend. **A check
that cannot fail is not a check** — the same lesson v0.20.0's CI wiring reached from the
other direction. It became real only when it was arranged so a specific number had to move.

**What carries forward** (→ `Backlog.md`):

- **Four documents have no card**, so they cannot be deleted from the Processing tab at all:
  `Axler-Measure-Integration`, `Durrett-Probability`, and two stuck at `converting`. That is
  the orphan problem from the other direction and it is not in this cycle's finding list.
- **One orphaned ingest directory** from 2026-07-17 with no source row — a 3.6 MB PDF left by
  a delete that predates this work. Evidence that B2/B6 were real.

One item carried in from [[v0.15.0 — Say what you did]]'s review: commit `37815b4`
("make whole-document jobs cancellable and stop deleted ones") already overlaps finding C6,
which belongs to v0.18.0. The overlap is noted there rather than here.

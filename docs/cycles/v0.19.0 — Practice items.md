## Problem

Learn Hub has exactly two graded activities — skeleton recall and concept recall — both
free recall → reveal → 4-button self-grade. That covers *remembering*, and it covers
nothing else. There is no way to practise **doing**: deriving a result, working a proof,
writing the code a chapter is teaching. For a textbook whose value is procedural, the app
can measure that you recognise the material and cannot tell you whether you can use it.

The reason it has never been built is that "generate practice problems" looks unbounded —
every subject needs its own notion of a correct answer, so the feature appears to require
solving math checking *and* code execution *and* proof validation before it ships anything.

**That framing is the bug.** Subject matter is not the axis. The axis is *how the answer
gets checked*, and that has about four values, of which the cheapest — self-graded against
a revealed worked solution — generalises to every subject and **is already the only
grading mode in this codebase**. A problem item is the existing three-beat loop with a
richer reveal. Everything else is an optional upgrade on the same row.

Two assets are already on disk and unused, which is why step 1 is not "build a table":

- `reading_guide.py` generates two grounded comprehension Q&A per section (schema
  `Check {q,a}`), has a registered `guides` job kind and three routes — **zero frontend
  consumers, `ext_guides` has 0 rows, never run.**
- `concept-detail.tsx:95-119` renders a complete "Test yourself" block with per-question
  reveal, bound to `ConceptLesson.questions`, hardcoded `[]` since `ext_concepts.
  quiz_questions` was dropped in the strip-down.

Prior art to respect: commit `99e4279` deleted seven study modules including a 421-line LLM
quiz author. It was cut for having **too many activities**, not because the idea was wrong.
This adds one.

## Appetite

Two sub-cycles, split at the point where the work stops being reversible.

**First**, generation + authoring — the user's stated priority is *creating* questions.
**Second**, making them gradeable. If the first overruns it sheds the editor polish, not
the generation.

Step 1 below is a spike inside the first cycle, not a cycle of its own: it is one enqueue
and a read, and its whole job is to kill the plan early if the answer is bad.

## Plan

**1. Light up `reading-guide` before building anything.** Run the existing `guides` job on
one real converted chapter and read the questions it produces. This costs an enqueue and
answers the assumption the entire design rests on: *is locally-generated question quality
good enough to build a pool around?* If it is not, the prompt is the work and the schema
was never the bottleneck — re-plan here rather than proceeding.

**2. `ext_practice` + generation.** One table, one `kind` column (`retrieve` | `problem`),
FK to `sources` so every cut of a book inherits, read through `concept_filter()`. New
`practice` job kind — six mechanical edits, no schema surprises. Per-section grain with
`coalesce=True`; the 2026-08-20 finding applies directly (per-block extraction fed the
model 558 chars instead of 8,073 and read as a model-quality failure).

**3. The Practice tab.** Third tab in `course-editor.tsx`, following `material-editor.tsx`'s
structure. `edited_at IS NULL` is the regenerable set — regeneration rewrites only untouched
rows, so polish is permanent. Answers render through the reader's `MarkdownReader`, never a
lookalike.

**4. Make them gradeable.** One `_TypedItem` entry, prefix `prac-`, `event_kind="practice"`.
Separate session, not a mixed queue: a ten-minute derivation must not land mid-run of
twenty-second concept cards. Two integration details are already verified —
`calendar.py:17` `_TYPES` must gain the type or it miscounts, and the reveal must read the
worked solution from `ext_practice` rather than snapshotting prose into
`concept_reviews.children`.

**5. Exam assembly**, only if wanted. Quiz/exam/practice are three *queries* over one pool,
not three data types; exam is the only one that may later deserve a stored row.

**Non-goals.** No code execution. No step ordering. No MCQ. No auto-grading, and **no LLM
in the graded loop** — `reviews.py:1` declares itself keyless and deterministic and that
property is worth keeping. Generation is LLM; doing is not. No second dead item type:
`ensure_chapter_item` already has zero callers and one ghost is enough.

## Exit criteria

1. A real converted chapter yields generated practice items of both kinds, grounded in its
   actual prose — judged by reading them, not by a row count.
2. An item edited by hand survives a regeneration of its section untouched.
3. A distilled custom version inherits its book's items with no generation run.
4. Practice grades move the activity heatmap and **do not** move coverage or retention.
   (Verified in design: `_retention_query` has no `item_type` filter so `prac-` rows do
   land in the retention map, but `summarize_memory` only looks up keys drawn from
   `ext_concepts`, so the extras are inert. Confirm it live rather than trusting this.)
5. Production fluency reports for a section with practice items, reads **unknown** for one
   with none, and moves neither coverage nor retention.
6. Per the standing rule — **render the real artifact.** Every one of these produces a
   plausible-looking value, so a green suite over fixtures proves nothing. Each check runs
   against a real book in the running app, images rebuilt first.

## The open question, now answered

It was: *should a practice grade feed a progress signal of its own?* **Yes — production
fluency, a fourth measure beside coverage / retention / state.** Decided 2026-08-25 and
designed in the spec; the short version is that `summarize_memory` is already pure and
`prac-` rows already reach the retention map, so the measure is the same function over a
denominator drawn from `ext_practice WHERE kind='problem'` — no new scheduler, no second
memory model.

Three constraints came with it and they are exit criteria, not preferences: it is **never
averaged into retention** (the season-long waypoint rests on retention meaning one thing);
**zero items reads as unknown, not as zero fluency** (an absent measurement rendered as a
bad score is precisely what the honesty arc exists to kill); and it **does not reuse the
0.9/0.7 retention thresholds**, which are calibrated for twenty-second cards and would call
a ten-minute derivation answered once "solid".

This is why the measure is designed now rather than after step 4. The ask behind this whole
cycle is a way to *audit your own understanding* — that is a measure, and steps 1–4 on their
own build only an activity.

## Build

_Filled in as it happens: decisions taken, and why._

### Step 1 — the spike. Run 2026-08-26. **Verdict: proceed, with the prompt as work.**

The `guides` job was run on a real chapter — *1 Introduction · Logic* of the math textbook
being studied, 98 sections, 110,519 characters — and produced **26 questions across 13
sections in 280 seconds** (~21s a section). `ext_guides` had held 0 rows since the feature
shipped; this is the first time anyone has seen its output.

**The questions are good enough to build a pool around.** Roughly three quarters are real,
answerable-from-knowledge questions about the subject:

> In the implication P → Q, under what specific condition is the statement false?
> How do you negate a universal statement (∀x. P(x)) according to the rules presented?
> What does Soundness guarantee about a logical system?
> What is the fundamental difference between propositional and predicate logic?

Those would work as retrieval cards today.

**The defect is a prompt habit, not a schema problem** — which is the fork this step existed
to decide, and it lands on the side the plan hoped for:

| | |
|---|---|
| refer to "the text" rather than the subject | **6 / 26 (23%)** |
| ask about the *section* rather than the material | 1 / 26 (4%) |
| carried mojibake | 2 / 26 (8%) — since fixed |
| answers under 8 words | 0 / 26 |

The 23% read *"According to the text, what does logic supply?"* — you answer those from
remembering this book's phrasing, not from knowing logic. One was worse: *"What is the
primary purpose of this introductory section regarding logic?"* is a question about the
document. Both are fixable by forbidding the construction in the prompt, and neither implies
anything about the item schema.

### The finding that matters more than the verdict

**Every one of the 26 is a retrieval question. Not one is a problem to work.**

That is not a defect — `reading_guide` was built to author comprehension Q&A and it did
exactly that. But it means the spike answered only half of what it was asked to. The design
splits items into `retrieve` and `problem`, and the whole argument for Competency is the
second kind: derive this, prove that, write the code. **This spike is evidence about
`retrieve` generation only.** Whether a local model can author a genuine *problem* from a
chapter is still completely untested, and it is the harder question.

So step 2 carried an explicit sub-spike before any of it was built. **It has now been run —
see below. Problem authoring works.**

### A bug the spike found in v0.20.0's fix

2 of 26 questions carried `Γ <0xE2><0x8A><0xA8> φ`. v0.20.0 wired `repair_model_text` into
`parse_concepts_response` and stopped there, so the reading-guide path kept storing the same
mojibake the fix was written to remove. **A fix that reaches one consumer of a shared problem
is not a fix.** Repaired in `reading_guide` and pinned by a test.

The 13 rows now in `ext_guides` were authored before that fix and two of them still carry it;
they regenerate on any future run, and the guard on this machine blocks the DELETE that would
force it sooner.

### Step 2 sub-spike — can it author a PROBLEM? Run 2026-08-26. **Verdict: yes.**

`scripts/spike_problem_items.py` — throwaway, writes nothing. Six sections across four books
(logic, SQL, systems design), ~16 problems, `nemotron-3-nano:30b`.

**It authors real problems.** From the logic chapter:

> Construct a complete truth table for (P → Q) ↔ (¬Q → ¬P). Show each row of P and Q, compute
> P → Q, compute ¬Q → ¬P, then evaluate the biconditional. State whether the final column is
> true in every row.

The worked solution was checked by hand and is **correct** — all four rows, both implications,
the identical-columns observation, the tautology conclusion. That matters more than the prompt
being well-formed: a plausible problem with a wrong solution is worse than no problem, because
self-grading has nothing to grade against.

From *Designing Data-Intensive Applications*, a Cypher query to write from a described graph.
From *Learning SQL*: *"If you replace UNION ALL with UNION in the same compound query, how many
rows will be returned? Explain why the result differs."* Both are work, not recall.

**The failure mode is specific, and it is not the one the falsifier predicted.** The worry was
recall wearing a problem's clothes across the board. What actually happens is that
**procedural/tutorial sections degenerate and content sections do not**. From *Learning SQL*'s
setup chapter:

> Write the exact command you would type in a Windows command window to log in to MySQL as the
> root user, **as shown in step 3 of Table 2‑1**.
> *Rubric: the answer must contain the exact string `mysql -u root -p`.*

That is remembering, with an imperative verb glued to the front. The same book's *union
operator* section — content rather than walkthrough — produced good problems, so this is a
property of the **section**, not the book or the domain.

It is also detectable. "As shown in step 3 of Table 2-1" is the same shape of tell as step 1's
"According to the text": a reference to the book's own furniture rather than to its subject.
Both can be forbidden in the prompt, and the prompt already permits returning an empty list.

**What this does not settle.** The model was never observed *refusing* — it found something to
work in every section, including two narrative ones. That was better than expected, but it
means the refusal path is untested, and a genuinely contentless section may yet produce an
invented task.

### Not built

Everything else. This cycle is planned, not started — the design predates the record (drafted
2026-08-22 as `PLAN — Practice items.md`, versioned 2026-08-25) and no code has been written
against it.

Step 1 is a spike, not a feature: run the existing `guides` job on one real converted chapter
and read what it produces. `ext_guides` holds 0 rows, so nobody has ever seen this model's
question quality, and the whole design rests on it being good enough to build a pool around.
If it is not, the prompt is the work and the schema was never the bottleneck — re-plan there
rather than proceeding.

## Test

_What was actually run, and what it said._

Suite: 171 passed, 1 xfailed.

**The step-1 spike closed by reading, not by a row count** — `ext_guides` going from 0 to 13
proves the job ran, not that the questions are worth answering. All 26 were read against
their sections and classified; the numbers are in Build above. The classification is the
evidence, not the verdict: a reader can disagree with "23% are meta-questions" by looking at
the list, which is the point of writing them all down.

# v0.23.0 — Items that check themselves

Sub-cycle plan under [[0.) Development Protocol 1.0]]
Opened 2026-10-16

Addresses **Competency**

> Each of item pool and production fluency holds on a real book: a chapter yields problems worth sitting down to, and the app tells me I cannot work one before the exam does

## Problem

Practice items are written in one LLM pass per section per kind, then screened by regexes
that catch FORM (furniture, deixis, no task). Nothing checks SUBSTANCE: a worked solution
that is wrong, a prompt the passage cannot answer, or a "problem" that is a definition in
disguise all reach the pool, and from the pool they reach the exam and the fluency number.
The last of these is the Competency falsifier itself, firing inside the measure, so it is
the failure that matters most.

The literature agrees with the shape of this (survey 2026-10-16, in chat): LLM-written items
carry item-writing flaws at high rates (ASEE 2026: only 54% of MCQs had fewer than two),
a critique → revise loop fixes most of it in the first two passes, round-trip answering
(Alberti 2019 and LLM successors) filters items whose answer does not survive a second
attempt, and objectives-first generation (DeepLearning.AI Quiz Generator V3) spreads items
across what a section teaches instead of clustering. No open-source tool fits this stack as
a drop-in; the techniques do.

The author model is also stale: `nemotron-3-nano:30b` was picked in August, and open weights
have moved since (Qwen3.8, gpt-oss-120b, DeepSeek-V4-Flash).

**Decided by the human, 2026-10-16:** build all four checks below; pick the model by a
bake-off on a real chapter, not a leaderboard; defer MCQ flaw rules + distractor metrics to
the MCQ cycle (Backlog); v0.23.0 *Set the paper* aborted to open this.

## Appetite

Two sittings of build, one bake-off run (model time, unattended), one human read of the
bake-off output. Shed order if it overruns: the second revise pass (keep one), then
objectives-first (the two gates are the point).

## Plan

All four are AUTHORING-TIME. Generation is LLM; doing is not — `reviews.py` and `exams.py`
are not touched.

0. **One pipeline function, no DB.** `author_section_items(heading, text, concept_lines,
   kinds, model) -> (items, receipt)` holds every stage below; `author_practice_sync` writes
   what it returns, and the bake-off script calls it without writing anything.
1. **Objectives first.** One call per section lists what it teaches, each objective tagged
   `recall` (state, define, distinguish) or `produce` (derive, apply, construct, decide).
   Recall objectives steer the retrieve prompt, produce objectives the problem prompt, one
   item per objective, at most 3. No objectives of a level → that kind is refused for the
   section without a call. Objectives are not stored.
2. **Critique → revise.** One call per kind per section hands the model its own items plus
   a flaw checklist (furniture, missing inputs, vague target, answer that skips steps,
   rubric that does not discriminate, difficulty off-scale) and takes back the same schema.
   `LEARN_PRACTICE_REVISE_PASSES`, default 1, max 2. The deterministic filters run AFTER.
3. **Answerability gate.** A fresh call answers each prompt from the passage, never seeing
   the stored answer; a second call compares the two. `contradicts` or `unanswerable` →
   dropped, counted `failedCheck`. A check that errors keeps the item and counts it
   `unchecked` — the receipt says so rather than pretending it passed.
4. **Recall-in-disguise.** For problem items, with the section's concept lines: does the
   worked solution only restate a definition (no derivation, computation, construction)?
   Yes → relabelled `retrieve`, counted `relabeled`. No concept lines → not checked.
5. **The receipt grows**: `{authored, dropped, refused, failedCheck, relabeled, unchecked,
   total}`.
6. **Bake-off.** `scripts/bakeoff_practice.py --doc --scope --model` runs the pipeline over
   one chapter, writes items + receipt to JSON, writes nothing to the DB. Candidates:
   `nemotron-3-nano:30b` (baseline) · `gpt-oss:120b` · `qwen3.8:27b-q8_0`. The winner
   becomes `LEARN_PRACTICE_MODEL` and `OLLAMA_MODEL`. `LEARN_EXTRACT_MODEL` stays gemma4:
   its speed constraint was measured and this cycle does not re-measure it.

**Non-goals.** MCQ, flaw rules for it, distractor metrics (deferred, Backlog). No new table
or column. No change to grading, exams, or fluency. No whole-book generation (anchored).
DeepSeek-V4-Flash is not in the bake-off: its 3-bit build is 129 GB against a ~120 GB budget,
and the 2–3-bit builds (97–103 GB) need the fleet stopped — the human's call, not this cycle's.

## Exit criteria

1. Unit: each stage tested with a stubbed model — objectives route kinds, revise output is
   re-filtered, the gate drops contradicts/unanswerable and keeps-and-counts on error,
   relabel fires only with concept lines.
2. Bake-off on one real chapter, three models: receipt table (kept · dropped · failedCheck ·
   relabeled · refused · wall time) pasted here, plus 10 items per model read by the human.
   The human picks.
3. The gate catches at least one real bad item on real data, pasted as a labelled example
   (or the record says it caught none and why that is believable).
4. The winner is set in compose; one chapter regenerated on :3001 from the editor; the
   Process tab receipt shows the new counters.
5. Guardrail: `git diff v0.22.1 -- backend/app/supplemental/study/reviews.py
   backend/app/supplemental/study/exams.py` touched by no commit of this cycle.

## Build

_2026-10-16, first sitting._ Rungs: the pipeline + four stages (`e4c7500`), the bake-off
script (`104faef`). Decisions taken on the way:

- **Stages live in their own module** (`practice_checks.py`) and return RAW items; the
  deterministic screen (`practice._clean`, factored out of `_author_section`) stays in
  `practice.py` and runs after authoring AND after each revise pass. Keeps the import one
  way and the screen in one place.
- **Objectives are per section, shared by both kinds.** One call, tagged recall/produce;
  a kind whose level has no objective is refused without an authoring call, so the
  objectives call pays for itself on descriptive sections.
- **The gate batches per kind per section** — one attempt call and one compare call, not
  two per item. Items are numbered and verdicts keyed by index; an item the model skips
  is `unchecked`, never passed.
- **A failed check keeps the item and counts it**; a failed revise keeps the unrevised
  items and counts them `unrevised`. Only a failed *objectives* or *authoring* call
  raises, exactly as authoring did before — there is nothing to keep.
- **Recall check is a classification, not a second answer.** The first idea — answer the
  problem from concept lines alone and compare — would relabel any problem a strong
  model can *compute* from a stated formula, which is application, not recall. The
  question asked instead is the falsifier's own: does the solution only restate a
  concept? Relabelled items carry `relabel` (the reason) in the bake-off JSON.
- **The job's receipt** keeps `authored/dropped/refused/total` and adds `failedCheck ·
  relabeled · unchecked · unrevised`; `total` still counts section × kind so the progress
  bar means what it did.
- **Bake-off chapter: *Classical Machine Learning* (AI 101 §5), chapter 3 — The
  Generalization Problem · Bias-Variance**, 7 sections, every one with extracted concepts
  (the recall check needs them). Not the §3 book v0.23.0-aborted used: its 105 verify-rung
  items are no longer in `ext_practice` (0 rows today), which this cycle did not cause and
  does not chase.
- **Smoke run** (nemotron, section 3 only): 163 s, 2 kept, 1 dropped by the screen, 0
  through the gate — the pipeline runs end to end against prod data read-only.

_2026-10-16, after bake-off v1._ Three candidates ran chapter 3 once each. The numbers
were not believable (gpt-oss: 17 kept, 16 dropped, **0** failed the gate, 9 unchecked),
so two gpt-oss sections were traced call by call before anything was compared. Misses,
each labelled:

- **MISS-1, empty attempt batch.** Section 3: the attempt call for three long problems
  returned `{"attempts": []}`. All three counted `unchecked` — honest, but the gate never
  ran. Fix (`7b27189`): any item missing from the batch gets one attempt on its own; a
  blank answer is not an attempt.
- **MISS-2, objectives that state their answers → items that give them away.** Section
  3.1: the objective was *"State the definition of bias … as the distance between the
  true value and the average prediction"*, and the item copied it: *"Define bias … as the
  distance between the true value and the average prediction … Use the description:
  'Bias at x₀ is how far the average …'"*. The gate passed it — the student agreed with
  the reference, which is all it was asked. Fix: the objectives prompt names the skill,
  not its answer; the compare step gets a fourth verdict, `gives_away`, which drops.
- **MISS-3, unanswerable-from-the-prompt passed.** A v1 gpt-oss item asked about *"the
  table reports a variance of 566"* with no table. The student sees the passage, so it
  could answer. Fix: `unanswerable` now names the case outright (relies on a table,
  figure, dataset, number or passage it mentions but does not include).
- **MISS-4, drops were uncounted reasons.** ~50% of items dropped, and no record of why;
  in the traces the same sections dropped 0 (run-to-run variance). Fix: every screen drop
  goes to `failed` with verdict `screened` and the matched tell, so the bake-off prints
  them.
- **Qwen3.8 stand-in disqualified on throughput**, not quality:
  `qwen3.8-abliterated:27b-32k` timed out on 6 of 7 sections (3 items in 76 min). Real
  `qwen3.8:27b-q8_0` needs an Ollama newer than the stack's 0.31.2 — an image upgrade,
  the human's call. Bake-off v2 is gpt-oss:120b vs nemotron-3-nano:30b.
